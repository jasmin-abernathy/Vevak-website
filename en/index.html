The idea

A digital fallback that does less, while keeping its rules understandable.

Many location-sharing tools depend on permanent Internet access, remote accounts and tracking infrastructure. VeVak explores a different route: use SMS and capabilities already present in Android, with local, time-limited and revocable authorisations.

How it works

Four steps. No magic.

The current VeVak core follows a small, bounded path.

  1. 01

    You choose the contacts

    The current prototype accepts up to five locally configured contacts. Each has its own number, normal request phrase and 24-hour, 7-day or 30-day authorisation.

  2. 02

    The SMS arrives

    VeVak locally checks the contact, their phrase, their authorisation and anti-tracking limits before taking action.

  3. 03

    The best available location information is selected

    A trusted Wi-Fi place can avoid a new lookup. Otherwise VeVak prefers recent data, compares Android's cache with its own locally remembered last position, and may then attempt one bounded current-location lookup. A remembered point is never presented as current: its age remains visible.

  4. 04

    A reply is sent

    If Android, the mobile network and the available location information allow it, VeVak replies by SMS. The request remains locally visible and automatic replies are globally capped.

Already in the free prototype

The safety baseline does not depend on a subscription.

These capabilities belong to the open-source build currently being validated, not to a future premium tier.

Multiple contacts

Up to five contacts in the current prototype, each with an independent authorisation duration, revocation control and normal request phrase.

Manual sharing

You can voluntarily send a one-time location to the selected contact after local confirmation, without waiting for an incoming request.

Encrypted backup

Configuration can be exported to a password-encrypted .vvk file and restored on another device. A restore never silently re-authorises contacts.

Anti-surveillance safeguards

Finite authorisations, local revocation, mandatory request visibility, hard rate limits and an optional duress phrase with a preselected fallback location.

Principles

Privacy is not an option buried in settings.

The project starts from a simple idea: the best sensitive data is often the data you never collect.

Local by default

The core does not require a VeVak account, VeVak server or permanent Internet connection.

No permanent tracking

Location is requested on demand. The current core does not perform periodic location tracking.

No ads, no trackers

No advertising SDKs, telemetry or user profiling.

FOSS first

The free/open-source variant remains canonical. Google components are isolated in the dedicated Play flavor.

!

Important limitations

VeVak is not an emergency service.

The core does not require Internet access, but it still depends on mobile-network/SMS availability, Android permissions and the phone's background restrictions. If Android Location services are switched off, VeVak cannot force a new location fix; depending on context it can only use a trusted Wi-Fi place already verified on the same connection or a still-usable locally remembered position.

In an emergency, use official emergency services and your phone's built-in emergency features.

Project status

Build, test and measure before expanding.

The prototype passes automated checks and real-device validation is now in progress.

Now · P0

Real-device validation

  • real SMS → location → reply, including screen-off use;
  • trusted Wi-Fi and remembered-location behaviour with Android Location switched off;
  • several senders and per-contact revocation;
  • dual-SIM / eSIM behaviour;
  • encrypted export/import across devices;
  • battery restrictions and accessibility.

Next · to design

Local VeVak+

Optional convenience features may be studied later, such as several trusted places, response profiles and advanced personalisation. They must never degrade the free safety baseline.

Research

Relay and device recovery

An optional encrypted Internet relay, cross-device convenience or selected recovery features will only be built if their usefulness and threat model are demonstrated.
